# 대여소 이용 데이터 ETL 파이프라인 개선안 (팀 통합)

## 1. 실행 구조

### 1.1 수집 기간 파라미터화
- **현재**: 수집 날짜가 `TARGET_DATES`로 코드에 고정되어 있음
- **문제**: 다른 기간의 수집이나 백필을 같은 DAG로 수행할 수 없음
- **개선**: `dag_run.conf` 등으로 시작/종료일을 외부에서 전달받도록 변경

### 1.2 Dynamic Task Mapping (`expand`) 적용
- **현재**: 하나의 태스크가 두 날짜를 순차적으로 수집
- **문제**
  1. 둘 중 하나만 실패해도 태스크 전체가 실패 처리되어, 성공한 날짜도 다시 수집함 (장애 격리 안 됨)
  2. 순차 실행이므로 소요 시간이 날짜 수에 비례해 늘어남
- **개선**: 날짜별로 독립된 태스크 인스턴스를 생성하여 병렬 실행, 실패한 날짜만 재시도

### 1.3 API 호출량/동시성 제어 (Airflow Pool)
- **문제**: 호출 제한 초과 시 HTTP 429가 발생하고 전체 수집 시간이 늘어남
- **개선**: Pool로 API 호출 태스크의 동시 실행 수에 상한을 걸고, 태스크 내부에도 요청 간 대기 또는 속도 제한을 적용
    - 병렬화와 함께 적용해야 병렬 확장이 API 부하로 이어지지 않음

### 1.4 페이지네이션 체크포인트
- **문제**: 페이지네이션 중간에 끊기면 1페이지부터 다시 수집
- **개선**: 진행 지점을 XCom에 저장해 실패한 페이지부터 재개

### 1.5 기간 단위 실행 잠금
- **문제**: `max_active_runs`는 같은 Airflow 환경 내 동시 실행만 제한. 개발/운영 등 여러 환경이 같은 기간을 동시에 적재하는 상황은 막지 못함
- **개선**: 기간을 키로 하는 DB 잠금 또는 실행 제어 테이블 도입

## 2. 데이터 품질 · 정합성

### 2.1 스키마 계약 검사
- **문제** : API 응답의 필드나 자료형이 예고 없이 바뀌면 변환 오류 또는 잘못된 집계가 발생함 
- **개선** : 변환 전에 필수 필드 존재 여부와 자료형을 검사하고, 예상 스키마와 다르면 태스크를 실패시킴

### 2.2 날짜별 수집 품질 검사
- **개선점** : 
    - 최종 집계 결과만 보지 않고 날짜별로 수집 건수, 정제 성공 건수, 제외 건수, 고유 대여소 수를 검사
        - API가 알려주는 전체 건수와 실제 수집 건수가 다르면 페이지네이션 누락으로 판단해 태스크를 실패시킴

### 2.3 품질 임계치 검사
- **문제** : 건수 일치, 제외 건수, 대여소 ID 유일성 등 기본 검사만 수행 
- **개선** : 운영 환경에서는 제외율/날짜별 수집량/대여소 수를 이전 실행 결과 또는 합의한 정상 범위와 비교해 비정상적인 급증/급감도 탐지한다.

### 2.4 DB 유니크 제약으로 중복 방지
- **개선** : `period_start_date`, `period_end_date`, `station_id` 조합에 유니크 제약을 설정해 동일 기간 재실행 시 대여소별 데이터가 중복 적재되지 않게 한다.

### 2.5 임시 테이블 경유 안전 적재
- **문제** : 최종 테이블에 바로 쓰면 적재 중 실패 시 일부 데이터만 남음 
- **개선** : 임시 테이블에 먼저 적재 후, 품질 검사 통과하면 트랜잭션으로 최종 테이블 반영 순으로 변경

### 2.6 자동 테스트 추가
- **개선** : 필수 값 누락, 숫자 변환 실패, 음수 값 제외, 대여소별 합산, 중복 적재 방지, API 재시도 로직 테스트
    - 특히 **같은 기간을 여러 번 실행해도 최종 행 수가 늘지 않는지(멱등성)** 확인

## 3. 운영 자동화 · 모니터링

### 3.1 스케줄 자동화
- 현재는 ETL을 수동 실행하고 있다. Airflow를 EC2에 올려 매일 지정 시각에 전날 데이터를 자동 수집하도록 한다.

### 3.2 실패 · 지연 알림
- **실패**: `on_failure_callback`으로 DAG명, 태스크명, Run ID, 오류 내용을 Slack 또는 이메일로 전달 
    - 장점 : 재시도 후에도 API 장애가 지속되면 담당자가 늦게 발견하는 문제를 막는다.
- **지연**: `execution_timeout` 안에 끝나더라도 평소보다 크게 늦어지면 데이터 제공 시각을 놓칠 수 있음
    - 장점 : 태스크별 예상 완료 시간을 정하고 별도 모니터링에서 지연 감지

### 3.3 실행 이력 테이블 (`etl_run_history`)
- 로그 외에 별도 테이블에 실행 기간, 수집 건수, 제외 건수, 적재 건수, 실행 상태를 저장해 실행별 처리 결과와 실패 이력을 조회할 수 있게 함.

### 3.4 정제 실패 Row 적재 (`station_usage_rejected`)
- **문제** : cleansing 실패 시 버려진 **개수만** 로그로 남긴다. 
- **개선** : 실패 데이터를 행 단위로 테이블에 적재 (SQS의 DLQ 같은 역할)

### 3.5 메트릭 · 대시보드
- **문제** : 로그만으로는 처리량 감소나 성능 저하를 빠르게 파악하기 어려움
- **개선** : 페이지 수, 수집 건수, 제외 건수, 적재 건수, 실행 시간, 재시도 횟수를 메트릭으로 전송하고 추이를 대시보드 시각화

### 3.6 데이터 계보 관리
- **문제** : 파이프라인이 늘어나면 데이터의 생성 경로 추적이 어려워진다. 
- **개선** : OpenLineage 등으로 API → Airflow 태스크 → 파일 → MySQL 테이블 사이 흐름 기록

## 4. 저장소 · 데이터 관리

### 4.1 원본/정제 데이터 저장소를 S3로 이전
- **문제** : 현재 원본 JSON과 정제 파일을 Airflow 볼륨에 쌓고 있어, 데이터 누적 시 로컬 디스크 용량 문제가 발생하고 작업 서버 디스크가 손실되면 결과 재현/장애 분석 불가능
- **개선** : Extractor가 로컬 디스크 대신 S3 버킷에 날짜별로 쓰도록 변경

### 4.2 보존 및 정리 정책
- **문제** : 원본 파일과 로그가 계속 쌓이면 디스크 부족으로 태스크,컨테이너가 실패
- **개선** : 보존 기간을 정하고 만료된 원본/중간 파일/로그를 주기적 아카이빙 또는 삭제

### 4.3 개인정보 필드 처리
- 분석에 사용하지 않는 `GENDER_CD`, `AGE_TYPE`은 수집 단계에서 폐기하거나 명시적으로 보관 기간 설정

## 5. 인프라 · 보안

### 5.1 Airflow Connections/Hooks 전환 
- MySQL 접속 정보를 환경변수 대신 Airflow 표준 Connection으로 관리 (UI/메타DB에서 관리)
### 5.2 커스텀 이미지 빌드
- **문제** : `_PIP_ADDITIONAL_REQUIREMENTS` 방식은 컨테이너를 띄울 때마다 pip install이 실행되어 느리고 네트워크 문제로 실패할 수 있음 
- **개선** : 의존성이 설치된 이미지를 빌드해 사용
### 5.3 DB 네트워크 격리
- **개선** : DB를 사설 서브넷에 두고 Airflow worker만 접근 가능하게 제한
### 5.4 IaC 도입 (Terraform)
- 인프라 구성을 코드로 관리해 환경 간 설정 차이 제거
### 5.5 컨테이너 리소스 제한
- CPU/메모리 상한을 걸어 특정 컨테이너가 다른 컨테이너 운영에 영향을 주지 않게 함
