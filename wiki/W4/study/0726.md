## Spark

### 발생 배경
- Hadoop
    - 대용량 데이터를 처리해야 할 필요성이 늘어남. 
        - 대용량 데이터를 스케일 업으로 처리하려면, 비용이 많이 들고, 시간 또한 많이 소요
        - 이 문제를 해결하고자 분산 처리 개념이 등장함.
            - 여러 대의 저렴한 기기로, 많은 데이터를 쪼개서 병렬로 처리하자.

- Hadoop의 한계
    - Map-Reduce 1번 수행마다 결과를 디스크에 작성해야 한다.
        - 여러 개의 처리가 연결되어 있거나, 같은 데이터를 반복해서 훑어야 하는 작업은 디스크 쓰기로 인한 시간 손해가 큼

- Spark의 등장
    - Hadoop보다 빠르게 실시간성으로 처리하고 싶다.
        - 중간 결과를 Disk에 쓰지말고, **메모리에 두고 재사용**하자. (In-memory 처리)

### Spark 특징
1. In-Memory처리
    - 필요할 때 메모리에 유지해 재사용
2. Unified Engine
    - 배치 처리, SQL 질의, 스트리밍, 머신러닝 등 모든 것을 Spark에서 처리 가능

### Spark 구조
1. Cluster Manager 
    - 자원을 관리하는 부분
    - Standalone, YARN, Kubernetes
2. Spark Core
    - 데이터 분산 처리, 스케줄링 등
    - RDD, 작업 스케줄링, 메모리 관리
3. Library
    - Spark SQL, Streaming, MLlib, GraphX 등

### Spark 특징 요약
1. 분산 처리 : 여러 대로 나누어 데이터를 처리한다. 
2. 인 메모리 : 하둡과 다르게 매번 디스크에 쓰지 않고, 메모리에 유지
3. 조각 단위 처리 : 데이터를 한 번에 전부 올리는게 아니라 조각 단위로 나누어 처리
    - 데이터를 파티션 단위로 한 번에 하나씩 훑으며 처리함
        - 한 노드가 파티션을 처리하는 경우에도 쪼개진 데이터 전체를 메모리에 올리지 않고, 레코드를 흘려 보내듯 처리
            - 메모리가 부족하면 디스크로 흘리기도 한다.(spill)

### Spark 구조
#### 1. Driver
> 어떤 일을 할 지 계획을 세우고, task로 나눠, 스케줄링 역할
>> Application 당 한 개 존재, Driver가 죽으면 Application이 죽는다.
- main이 실행되고, `SparkSession`이 생성되는 프로세스
    - Q) Spark Session이란?
- 하는 일
    1. 사용자 코드 -> 논리적 실행 계획(DAG)으로 변환
    2. `DAGScheduler` : DAG를 **셔플 경계 기준**으로 **Stage**로 **분할**
    3. `TaskScheduler`: 각 **task를 Executor에 배정**
    - 그 외
        - Executor 상태 추적
        - 실패 task 재시도
        - Spark Web UI 호스팅
        - 결과 회수
#### 2. Executor
> Driver가 시킨 task를 실제로 수행, 자기가 맡은 데이터를 메모리에 들고 있다가 결과 보고 
- 특정 Appliaction을 위해 Worker Node에 뜨는 JVM 프로세스
    - App이 끝날 때까지 살아있다.
- 특징
    - 고정된 코어수(slot)를 갖는다.
        - 이 코어수가 동시에 처리 가능한 task 수를 결정
- 역할
    1. Driver가 배정한 task 실행 후, 결과 반환
    2. 캐시된 RDD/DataFrame을 위한 인메모리 저장소 제공
#### 3. Cluster Manager
> Driver 요청에 따라서 Cluster의 자원을 할당하고 Executor를 띄움
>> Standalone, YARN, Kubernetes가 해당
- Cluster 자원을 확보, 배분하는 외부 서비스
- 종류
    - Standalone
    - YARN
    - Kubernetes

#### df.collect()가 위험할 수 있는 이유
1. Driver OOM
    - `collect`를 사용하면 모든 파티션의 데이터를 네트워크를 이용하여, Driver의 JVM 힙 하나에 전부 모은다.
        - Driver 메모리는 보통 데이터보다 훨씬 작다
            - collect 사용시 Driver OOM 발생 가능
2. 병목
    - 전 데이터가 한 노드로 몰리기 때문에 병목 발생 가능
- 대안
    1. `show()`,`take(n)`,`limit(n).collect()`로 일부만 확인
    2. 아예 스토리지 `write`

### Spark 연산
#### 1. Transformation
- DataFrame/RDD를 입력받아 새로운 DataFrame/RDD 반환하며 lazy된다.
    - Q) lazy란?
        - Transformation을 호출해도 그 순간엔 아무 계산도 하지 않고, 계획만 작성
        - 실제 계산은 action에 한 번에 실행된다.
    - Q) lazy를 분리한 이유
        - 최적화를 위해서
            - 매번 즉시 실행이면 다음 연산이 무엇인지 모르고 앞의 것만 처리함
            - 실행을 몰아서하면, action 호출 시점에 전체 연산을 한 번에 보고 최적화가 가능
            - 이러한 최적화를 Catalyst Optimizer가 한다.
        - 요약
            - Transformation은 lazy해서 호출 시점에 계산하지 않고 lineage/DAG만 구성하고 action이 호출될 때 전체 계획을 최적화한 뒤 한 번에 실행한다. 
            - 이를 통해 전역 최적화가 가능해진다.
    - Q) lazy 결과 저장
        - Spark는 lazy이기 때문에 결과를 저장해두지 않는다.
            - 이로인해 **Action을 두 번 호출 시** **전체가 처음부터 두 번 실행**된다.
        - 이 결과 저장의 문제를 해결하기 위한 것이 `cache`와 `persist`
- Transformation 예시 : `select`,`filter`,`groupBy`,`join` 등
    - 호출해도 아무 계산도 실행되지 않고 DAG로만 저장
#### 2. Action
- 값을 Driver로 반환하거나 Storage에 쓰며, **즉시 실행 트리거**
- Action, Transformation 구분
    - 다른 DataFrame/RDD 반환 : transformation
    - 다른 값을 반환하거나 씀 : action
#### Lazy Evaluation 덕분에 가능한 최적화
1. Shuffle 없는 연산을 하나의 Stage로 pipelining
2. Predicate/Projection Pushdown : Filter, Column 선택을 Data Source에서 진행 
    - Q) Predicate Pushdown?
        - Spark가 데이터 소스에 최대한 가깝게 filter를 적용하려 하는 것
        - 이를 통해 데이터의 모든 행을 읽는 것 대신에 관련 없는 데이터를 안 읽고 **원하는 데이터가 있을 가능성이 높은 행 그룹만 읽는다.**
    - Q) Projection Pushdown?
        - Spark가 요구되는 column만 읽는 것
        - 아래와 같이 작성하면, 500개 컬럼이 있어도 name이랑 age만 읽는다.
            ```python
            df = spark.read.parquet("users.parquet")
            df.select("name","age").show()
            ```
        - Benefit : disk I/O, memory 사용량, 처리 감소
3. Column Pruning
    - 계산에 불필요한 컬럼을 제거함.
    - Q) Projection Pushdown이랑 뭐가 달라?
        > 실행되는 layer가 다르다.
        - Column Pruning : Query Plan Optimization
        - Projection Pushdown : Data Source Optimization
        - Column Pruning 이후에 Projection Pushdown이 일어나는 것
            - 아래와 같이 써있어도, country는 실제로 사용되지 않으니까 실행 계획에서 제거됨
            - Projection Pushdown은 위와 같이 실행 계획이 결정되면 소스에서 읽을 때 사용되는 것
4. Shuffle 횟수 최소화

### 실행 모델
> Application -> Job -> Stage -> Task

- Application
    - 하나의 `SparkSession`
    - 자기 전용 Executor 집합을 받음
- Job
    - 하나의 Action이 하나의 Job을 Trigger한다.
    - 즉, 실행된 Action 개수 == Job 개수
- Stage
    - 하나의 Job은 Shuffle 경계를 기준으로 **여러 Stage로 분할**된다.
    - 한 Stage 안에는 **셔플 없이 연속으로 파이프라인 가능**한 **narrow 변환들**만 존재
        - **데이터를 재분배해야 하는 지점**마다 **새 Stage**가 시작
- Task
    - 실행의 최소 단위
    - Task = Stage의 연산을 한 파티션에 적용한 것
        - Stage의 Task 개수 == Stage의 파티션 개수
    - Task들은 Executor 코어에서 병렬로 동작

### 셔플과 의존성
- 의존성 : 자식 파티션이 어떤 부모 파티션에 의존하는가
#### Narrow Dependency
- 부모 파티션 하나가 자식 파티션 하나에만 기여
    - ex, map, filter, select, union 등
- 각 파티션이 독립적으로 처리
    - 데이터를 노드 간 이동할 필요 X, 여러 개를 한 Stage에서 연속 파이프라인으로 처리
#### Wide Dependency
- 자식 파티션 하나가 부모 파티션 여러 개에 의존
    - ex, groupBy, reduceByKey, join, distinct, repartition 등
- 같은 key를 같은 파티션으로 모으기 위해 데이터를 재분배 해야 함. (shuffle)
    - shuffle이 비싼 이유
        - Data를 Disk에 작성 -> 네트워크로 전송 -> Shuffle Read
        - 디스크 I/O, 네트워크 I/O, 직렬화 모두 끼니까 Spark에서 가장 느린 연산

### RDD (Resilient Distributed Dataset)
- RDD
    > 여러 노드에 **분산**된, **불변**이고, **병렬 처리 가능**한 객체들의 컬렉션
    - Resilient(회복력 있는) : 노드가 죽었을 때 데이터를 복제해두는 대신 lineage를 이용하여 잃어버린 파티션만 재계산하여 복구
    - Distributed(분산된) : 데이터가 여러 파티션으로 쪼개져 흩어져있음
    - Dataset(데이터셋) : 처리할 레코드들의 모음이다.
        - Record : Schema가 없는 임의 객체
    - RDD는 데이터 자체라기보단 `데이터를 어떻게 만드는가에 대한 정보`가 가깝다.
- 주요 속성 5개
    1. 파티션 목록 : 데이터를 나눈 조각들, 병렬 단위
    2. 각 파티션에 적용할 compute 함수 : 실제 연산 
    3. 다른 RDD에 대한 의존성 : narrow/wide dependency
        - lineage가 여기서 나온다.
    4. (Optional) Partitioner : key-value RDD에서 파티셔닝 방식 (Hash/Range)
    5. (Optional) preferred locations : 데이터 지역성, 이 파티션은 이 노드에서 처리하는게 좋다라는 힌트
- 최근엔 RDD를 거의 사용하지 않고, DataFrame을 사용한다.
    - Why?
        1. 최적화 불가
            - Schema가 없고 연산의 의미를 몰라 Catalyst Optimizer가 개입하여 최적화를 할 수 없다.
                - 개발자가 작성한 순서대로 실행
        2. 직렬화, 메모리 비효율
            - JVM 객체로 다뤄 메모리를 많이 사용하고 Garbage Collector 부담이 큼
        3. 저수준 API
            - 최적화를 개발자가 책임져야 한다.
    - DataFrame 장점
        1. Schema가 있다. 
            - RDD + Schema + Catalyst + Tungsten 합친 것
            - Q) Schema란?
                - DataFrame의 각 컬럼 이름과 데이터 타입을 정의한 구조
                - `df.printSchema()`로 확인 가능
            - Q) Schema Inference
                - CSV,Json을 읽을 때 `inferSchema=True`로 Spark가 데이터를 한 번 훑어서 타입을 추측하도록 할 수 있다.
                - 단점
                    1. 데이터를 추가로 1회 스캔하기 때문에 느림
                    2. 타입을 잘못 추론할 수 있음
                        - 스키마를 직접 정의해 넘기는 **명시적 스키마 지정**을 실무에서 많이 사용한다.
                            ```python
                            from pyspark.sql.types import StructType, StructField, IntegerType, StringType

                            schema = StructType([
                                StructField("id",   IntegerType(), False),   # False = not nullable
                                StructField("name", StringType(),  True),
                            ])
                            df = spark.read.csv("users.csv", header=True, schema=schema)
                            ```
                - 참고) Parquet이나 ORC같은 Column형 포맷은 스키마 자체를 파일에 담고 있기 때문에 추론이 필요없고 빠르다.
    - 그럼에도 불구하고 RDD를 사용하는 경우
        1. Schema로 표현하기 어려운 완전 비정형 데이터
        2. `파티션, 저수준 실행`을 `아주 세밀하게 직접 제어`해야 할 때
        3. 오래된 레거시 코드

### DataFrame과 Dataset
- RDD/DataFrame/Dataset 비교

|구분|RDD|DataFrame|Dataset|
|---|---|---------|-------|
|스키마|없음|있음(컬럼,타입)|있음|
|타입 안정성|Compile Time|Runtime(약타입)|Compile Time(강타입)|
|Catalyst|불가|가능|가능|
|Tunsten|불가|가능|가능|
|언어| 모든 언어|모든 언어|Scala/Java만|

- Q) 강타입, 약타입
    - 강타입
        - 타입 오류를 실행 전에 잡아줌
    - 약타입 
        - 실행부터 하고, 문제 지점에 도달했을 때 터짐

- Dataset과 DataFrame의 차이 : 타입 안정성
    > DataFrame은 Dataset[Row]의 별칭(Scala 기준)
    - Python은 동적 언어이기 때문에 컴파일 타임 검사가 없다.
    - 그래서 PySpark에서는 DataFrame과 Dataset의 차이가 없다.

### Catalyst Optimizer
> Spark SQL의 쿼리 최적화 엔진

#### 동작 순서
> 확인 방법 : `df.explain(True)`
1. 사용자 코드 -> Unresolved Logical Plan 
    - 뼈대 트리만 생성
    - 이 단계에서는 실제로 존재하는 Column인지, 타입이 무엇인지 등을 고려하지 않음
2. Analysis(Unresolved -> Resolved) : Column, Table 이름을 Catalog와 대조해 해석
    - 실제로 존재하는 Column인지 확인
    - 각 Column 데이터 타입 결정
    - 어떤 테이블에 속하는 Column인지 결정
    - Q) Catalog?
        - 위 행동을 하기 위해 참조하는 메타데이터 저장소
        - 종류
            1. 임시 카탈로그
                - createOrReplaceTempView로 만든 임시 뷰
                - 세션 안에서만 유효함
            2. 영구 카탈로그
                - Hive Metastore에 등록된 영구 테이블 메타데이터
3. Logical Optimization : 규칙 기반 재작성 
    - 미리 저장된 변환 규칙들을 적용하여 더 효율적인 형태로 변경
    - 비용은 계산하지 않고, 기계적으로 계획트리에 매칭되는 패턴이 없을 때까지 반복 적용
    - 대표 규칙
        1. Predicate Pushdown : Filter를 DataSource에 가깝게 적용 (읽는 시점에 적용)
        2. Projection Pushdown, Column Pruning : 쓰는 것만 읽기
        3. Constant Folding : 미리 계산될 수 있는 상수는 미리 계산해둠
            - `x + 2*3` -> `x + 6`으로 변경
        4. Boolean/식 단순화 : 
            - `WHERE true AND age > 30` -> `WHERE age > 30`으로 변경
4. Physical Planning : 물리 계획 여러 개 생성 후, cost plan이 가장 좋은 것을 하나 선택
    > CBO (Cost-Based Optimization)
    - 예시 : Join 선택 
        - Broadcast Hash Join : 한쪽 테이블이 작으면 그걸 모든 Executor에 복사(셔플 회피)
        - Sort-Merge Join : 양쪽이 다 크면 정렬 후 병합(셔플 발생)
        - Shuffle Hash Join : 특정 조건에서의 해시 조인
    - Catalyst는 통계를 보고 전략을 판단함.
        - 문제 : 통계가 적으면 부정확함.
            - 해결 : AQE 도입으로 런타임 중 계획 재조정
            - 현재 : 여러 물리 계획을 비용 모델로 비교해 최선을 선택 -> AQE로 런타임 재조정
5. Code Generation : 선택된 계획을 JVM 바이트코드로 컴파일

### Tungsten
> 어떻게 실행할지(CPU,메모리) 최적화

#### 하는 일
1. Off-heap 메모리 + 바이너리 포맷
    - 데이터를 UnsafeRow(Compact한 바이너리 파일)로 관리한다.
    - 장점 : JVM 객체 오버헤드와 GC 부담 감소
    - Off-heap : JVM 힙 바깥에 직접 할당하는 raw 메모리
        - 특징
            1. GC 대상 X
            2. 객체 오버헤드 없음
        - 장점 : GC를 우회하고 객체 오버헤드를 제거해서, 메모리 효율과 실행 안정성을 높임
        - Q) 힙에 있으면 왜 안좋지?
            1. GC pause
                - heap에 존재하는 것은 GC가 주기적으로 관리하는 영역
                - 데이터가 늘어날수록 GC부담이 커져, pause 걸릴 수 있다.
            2. 메모리 낭비
                - JVM 객체는 실제 데이터보다 훨씬 많은 메모리 차지
2. 캐시 친화적 연산
    - CPU 캐시를 잘 타도록 데이터 배치 최적화
        - 데이터를 잘 읽을 수 있게 바이너리로 연속된 메모리에 촘촘히 배치

3. Whole-Stage Code Generation
    - 한 Stage의 여러 연산자를 하나의 함수로 합쳐 컴파일
        - 연산자마다 발생하는 함수 호출 오버헤드를 제거하여 속도가 빨라짐
